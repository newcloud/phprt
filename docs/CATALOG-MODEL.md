# catalog 数据模型与分发

状态：阶段 0 / 阶段 1 已实现（2026-11-21）。阶段 2 的快照 id、manifest、签名和 CDN 见
[CATALOG-SNAPSHOT.md](CATALOG-SNAPSHOT.md)（未排期）。

目标读者：维护 catalog 的人、实现 catalog 分发的人，以及需要判断「用户该跑哪条命令」
的人。

## 摘要

- `install` / `update` 在真正要下载或编译前问一次；`y` 只取本次闭包用到的已发布组件
  分片，更新本地 catalog，重新算方案，再下载源码、构建；`n` 用本地。
- `add` 在已安装的产品上会立即编译，所以同样询问；产品还没安装时只记方案，不询问。
  `remove` 只有需要重编时才问，默认 `n`；只删产物时直接完成。
- 用户不查上游、不运行 `catalog update`、不计算 sha256。sha256 由维护者
  `catalog update` 算好，`catalog publish` 随组件分片一起发布。
- 阶段 1 的完整性依赖发布主机和 HTTPS；manifest、签名、快照 id 在阶段 2。
- 不想每次看到询问：`phprt.toml` 里 `[catalog] ask_before_online_update = false`，或命令
  加 `--no-refresh`；`--lock` / `--offline` 也直接跳过交互。

## 用户视角

这一节描述阶段 1 的实际用法。

### install

```text
准备安装 php 8.5，会用到这些组件：
  php 8.5        本地 8.5.12
  openssl 3.5    本地 3.5.9
  libcurl 8.23   本地 8.23.0

安装前是否在线获取最新补丁版本？(y/n，回车默认 y)
只获取这些组件的版本清单，不下载源码。
```

- 回车 / `y`：只取上面这些组件的分片，更新本地 catalog，重新算方案，再下载源码、构建。
- `n`：不联网，直接用本地 catalog。本地 catalog 里比已装版本新的补丁仍然会用。
- 已装过一部分时，对应行显示「已装」，例如 `openssl 3.5  已装 3.5.9`。
- 产品已经装好、这次方案也没有变化时，不会出现这个询问；按重复安装的现有提示处理，
  升级补丁用 `update`。显式 `--refresh` 不受这条限制，仍然取一次。

### update

```text
php 8.5 当前安装：
  php 8.5.12     本地 8.5.13  ↑
  openssl 3.5.9  本地 3.5.9   =
  libcurl 8.23.0 本地 8.23.1  ↑

升级前是否在线获取最新补丁版本？(y/n，回车默认 y)
只获取这些组件的版本清单，不下载源码。
```

`↑` 表示本地 catalog 已有更新，`=` 表示已是最新。输入 `y` 后只取当前闭包的分片，更新
本地 catalog，重新算方案再构建。

### add

已安装的产品上，`add` 会立即编译，所以编译前询问：

```text
$ phprt add php@8.5 swoole
准备加入 swoole，会用到这些组件：
  php 8.5        已装 8.5.12
  swoole 6.2     本地 6.2.0

加入后会立即编译。是否先获取最新补丁版本？(y/n，回车默认 y)
只获取这些组件的版本清单，不下载源码。
```

产品还没安装时，`add` 只记方案，不下载、不编译，也不询问：

```text
$ phprt add php@8.5 swoole
已加入 swoole（shared）；这个版本还没装过，先 phprt install php@8.5
```

### remove

只删产物、不需要重编时，不询问：

```text
$ phprt remove php@8.5 swoole
已移除 swoole（shared），删掉 2 个文件：
  ...
```

需要重编时，先问是否顺便获取剩余闭包的补丁（默认 `n`），再用现有提示确认重编：

```text
移除后需要重新构建，会用到这些组件：
  php 8.5        已装 8.5.12
  openssl 3.5    已装 3.5.9

是否顺便获取剩余组件的最新补丁？(y/n，回车默认 n)
只获取这些组件的版本清单，不下载源码。
```

默认 `n`：移除就是移除，不顺便升级别的组件。

### 获取时显示

只取本次闭包用到的组件分片。并发规则和 `catalog update` 一样：最多 10 个组件，同一主机
最多 2 个连接。开始时先把任务列出来，再逐行推进：

```text
正在获取 catalog 更新（3 个组件）：
  [catalog] php 8.5        等待
  [catalog] openssl 3.5    等待
  [catalog] libcurl 8.23   等待

  [catalog] openssl 3.5    获取中
  [catalog] php 8.5        获取中
```

完成时结果直接替换进度行，按实际完成顺序显示：

```text
  [catalog] openssl 3.5    ✓ 3.5.9 → 3.5.10
  [catalog] php 8.5        ✓ 8.5.12 → 8.5.13
  [catalog] libcurl 8.23   ✓ 已是最新 8.23.0

catalog 已更新，继续下载并构建。
```

单个组件失败不阻断，失败行带原因：

```text
  [catalog] php 8.5        ✗ 获取失败：网络超时，继续用本地 8.5.12
```

有组件失败时，结束前再打印一行汇总。其它组件都没更新时，括号里是本地数据时间：

```text
1 个组件没有取到，继续使用本地数据（2026-11-20T10:00:00Z）。
```

已经有一部分组件取了新数据时，只说失败的行继续用本地版本；`stamp` 记的是这批新数据的
时间，不能当成失败组件的数据时间：

```text
8 个组件没有取到，继续用本地版本。
catalog 已更新，继续下载并构建。
```

没有更新：

```text
没有发现新补丁，继续。
```

非终端（CI、管道）退化成一行一个：

```text
[1/3] [catalog] openssl 3.5 获取中
[catalog] openssl 3.5 ✓ 3.5.9 → 3.5.10
[2/3] [catalog] php 8.5 获取中
...
```

### 下载和 sha256

检查阶段只取 catalog 分片，不下载源码；分片里已经有每个补丁的 `url` 和 `sha256`。
源码包在检查完成、catalog 更新、方案重算之后才下载，下载时按分片里的 `sha256` 校验。

用户侧不计算、不回填哈希。分片里某个补丁缺 `sha256` 时拒绝使用该补丁并提示等待维护者
修复，不会下载源码去补哈希。

## 1. 两类使用者

catalog 同时服务两种人，他们的目标、频率和失败承受能力完全不同：

| | 维护者 | 用户 |
| --- | --- | --- |
| 关心 | 所有组件、所有已有线、sha256 是否齐全、数据能否审计 | 自己产品的闭包能否升到最新补丁 |
| 不关心 | 用户装的是哪个产品 | 上游接口、sha256、没用到的组件 |
| 频率 | 发版前、每日 CI | 想升级时，最好零操作 |
| 网络 | 必须能访问全部上游 | 只访问发布主机，或完全离线 |
| 失败 | 可以部分成功、重跑、人工处理 | 单个组件失败不能阻断安装 |
| 产物 | `catalog.toml` 的改动、发布分片 | 本地 catalog 的组件分片 |

边界：

- `catalog update` 是维护者命令：查上游、算 sha256、写仓库、备份。
- `catalog publish` 也是维护者命令：把单文件拆成组件分片，不改内容。
- 用户的在线检查只取分片、只写本地 catalog，不访问上游、不写仓库、不算哈希。
- 用户在 `install` / `update` / `add` / `remove` 里确认检查，不直接运行维护者命令。

## 2. 现在的问题

### 2.1 用户拿不到新补丁

`install` 和 `update` 只读仓库里的 `catalog.toml`。用户装完以后，补丁数据就停在发行时
那份；没有「只更新数据、不动代码」的通道。`update` 仍会打印「已是最新」，用户没有信号
知道数据过期了。

### 2.2 让用户跑维护者命令不合适

`catalog update` 会扫描全部组件、访问几十个上游、下载补丁包算哈希、改仓库文件、写备份。
这是维护者的工作：

- 用户网络要能到 GitHub API、PECL、php.net、GNOME 等全部源；
- GitHub 匿名接口每小时 60 次；
- 发行包、只读安装、容器里的 recipes 可能不可写；
- `recipes/upstream/*.star` 要和二进制版本匹配。

用户需要的只是「我这个闭包有没有新补丁」。

### 2.3 没有来源和日期

今天的「最新」等于「我本地这份文件此刻的内容」。两个用户在同一时间装，可能拿到不同
补丁；支持人员拿到 state 也无法知道当时用的是哪份数据。

## 3. 设计原则

1. **数据生产与数据消费分开。** 查上游、算哈希、写仓库只发生在维护者或 CI；用户只读
   发布数据。
2. **用户只读发布数据。** 阶段 1 是组件分片，阶段 2 是带 manifest 和签名的快照；用户
   交互不变。
3. **用户只为自己的闭包付成本。** 只取本次用到的组件分片，不取其它产品，也不取上游。
4. **产品 / 系列是视图，不是存储分区。** 组件（openssl、libcurl）被多个产品共享；按
   产品拆会把同一份数据复制多份。
5. **单文件继续做维护者的源，分片做发布物。** 人工编辑和 review 不倒退，机器获取变细。
6. **追加，不删除。** 旧补丁保留；发布文件可以覆盖，但内容只增不减。`--lock` 和旧安装
   才有源码可查。
7. **默认询问，可跳过。** 真正要下载或编译时问一次；不构建就不问；`--lock` /
   `--offline` / `--no-refresh` 和配置都能跳过。
8. **检查只动 catalog，下载才动源码。** 检查阶段不下载源码；确认后才下载并校验。
9. **哈希由发布方提供。** 用户只校验，不计算、不回填。

## 4. 目标模型

### 4.1 三层

| 层 | 谁产生 | 形态 | 生命周期 |
| --- | --- | --- | --- |
| 源 | 维护者 | `recipes/catalog.toml` + `recipes/upstream/*.star` | 跟随代码仓库 |
| 发布 | 维护者 / CI | 组件分片目录 | 每次发布覆盖 `latest` |
| 本地 | 在线检查 / 随包基线 | `.phprt/catalog/components/<组件>.toml` | 随安装根，可删除重建 |

recipe、bundle 仍然是代码，回答「允许哪些线、默认哪条线、怎么编译」；catalog 只回答
「这条线现在有哪些补丁、从哪下载、哈希是多少」。

阶段 1 的本地数据来自发布分片；随包基线仍然是 `recipes/catalog.toml`。

### 4.2 分片粒度

最小分片是**组件**，不是产品，也不是线。

- 不按产品拆：openssl 被 php 和 nginx 共用，zlib 被 php 等多个产品共用；按产品拆会
  重复存储。
- 不按线拆：一次上游查询本来就覆盖该组件的全部线（见 CATALOG-UPDATE 第 5 节），拆成
  `openssl-3.5.toml`、`openssl-4.0.toml` 只会增加文件和一致性问题。
- 按组件拆：正好对应 upstream 脚本、下载缓存目录和报告里的失败单位。

闭包由客户端算：从 recipe 元数据、bundle 默认值、state 实际选择求出组件名，再取同名
分片。**这个映射不存进 catalog**，否则等于把求解器复制一份到数据里。bundled 组件没有
catalog 条目，不需要分片。

### 4.3 发布物布局（阶段 1）

```text
catalog/latest/
├── stamp                       # 本次发布的时间
└── components/<组件>.toml
```

分片就是 `catalog.toml` 里该组件的 `[组件]` 段，带组件名表头，格式相同，可以直接解析：

```toml
[openssl]
"1.1.1" = [ { version = "1.1.1w", url = "https://...", sha256 = "..." } ]
"3.5" = [
    { version = "3.5.9", url = "https://...", sha256 = "..." },
    { version = "3.5.10", url = "https://...", sha256 = "..." },
]
```

`stamp` 只记发布时间，不参与解析；分片段本身是确定性的。

阶段 1 没有 manifest，也没有分片自身的哈希：分片完整性由 HTTPS 和发布主机保证。主机被
控制等价于代码仓库被控制；要更强的保证，等阶段 2 的 manifest 和签名。

### 4.4 本地目录

```text
.phprt/catalog/
├── stamp                       # 最近一次成功获取的时间
└── components/<组件>.toml      # 已获取的分片
```

解析时以 `recipes/catalog.toml` 为基线，再叠加本地分片：

- 按组件、按线取并集；本地分片里的补丁追加到基线后面。
- 同一组件、同一线、同一版本在两边都有时，`url` 必须一致；基线缺 `sha256` 时由分片
  补上，两边都有哈希且不一致时直接报错，提示删掉该分片后重新检查。
- 基线比本地分片新时不会被降级；旧补丁仍然保留。
- 取到分片后先校验格式、每条补丁都有 `url` / `sha256`、和基线没有哈希冲突，通过才
  rename；某个组件失败时保留它上一次的分片，其它组件照常更新。
- `stamp` 只记最近一次真正写入新数据的时间。

本地 catalog 是缓存，不是仓库文件；删掉 `.phprt/catalog/` 就回到随包基线。

### 4.5 发布规则（阶段 1）

`catalog publish --out <目录>` 只做数据变换，不访问上游：

- 输出到 `<目录>/latest/components/<组件>.toml`，每个组件一个文件；
- 文件包含该组件的全部线和全部补丁，不裁剪、不删除；
- 每条补丁都必须有 `url` 和 `sha256`，缺一条就失败，不生成发布物；
- 分片段是确定性的（组件和线按名字排序，补丁按版本排序），重复执行字节一致；
  `latest/stamp` 记录本次发布时间；
- 上次发布里多出来、这次 catalog 没有的 `.toml` 会从组件目录删掉；
- 不写 `recipes/catalog.toml`，不改 recipe、bundle、state。

发布目录原样上传到静态主机即可；内网镜像复制同样的路径。

## 5. 命令面

| 谁 | 命令 | 做什么 |
| --- | --- | --- |
| 维护者 | `catalog update` / `catalog publish` | 查上游、算 sha256、写源 catalog、发布组件分片 |
| 用户 | `install` / `update` / `add` / `remove` | 取闭包分片、下载、构建 |

`catalog update` 不在用户路径里；用户命令不会查上游，也不会写仓库里的 `catalog.toml`。

### 5.0 交互检查

`install` / `update` / 已安装产品上的 `add` / 需要重编的 `remove` 在下载或编译前询问
一次。检查范围只限本次闭包用到的组件。

```text
算方案 → 判断这次会不会下载或构建
  → 不会：不询问，直接给出结论（显式 `--refresh` 仍取一次）
  → 会：询问 → y 取分片并更新本地 catalog → 重新算方案 → 下载源码 → 构建
```

`plan`、`list`、`graph`、`scheme`、`audit` 是只读命令，不询问、不联网。

#### 5.0.1 install

- 已安装且方案一致：不询问；按现有提示处理（重新安装用 `--force`，升级用 `update`）。
- 首次安装、安装树需要修、或本地 catalog 已经有更新（构建会发生）：询问。
- `--downloads` 只下载源码、不写 state；只要会下载，就询问。

#### 5.0.2 update

`update` 本身就是升级入口，默认询问；`--offline` / `--no-refresh` 和配置照样能跳过。
`update` 不接受 `--lock`。

#### 5.0.3 add / remove

- `add`：安装树存在时会立即编译，询问；安装树不存在时只记方案，不询问、不下载源码
  （显式 `--refresh` 仍会取一次 catalog）。
- `remove`：不需要重编时直接完成，不询问；需要重编时，先问是否顺便获取剩余闭包的补丁
  （默认 `n`），再按现有提示确认重编。这个询问不受 `default_answer` 影响，固定默认不
  顺便升级。

#### 5.0.4 并发和显示

- 最多 10 个组件同时获取；同一主机最多 2 个连接。
- 复用 `phprt_download::HostGate` 和 `host_bucket`。
- 开始时先把任务列出来，状态从「等待」切到「获取中」，完成后显示 `✓ 3.5.9 → 3.5.10`
  或 `✓ 已是最新`；失败显示 `✗` 和原因。
- 单个组件失败不阻断：保留该组件上一次的分片，安装继续。
- 失败行带原因；完成的组件按实际完成顺序显示。
- 非终端退化成一行一个组件的开始和结束，不会长时间没有输出。

#### 5.0.5 配置和参数

项目根（`--root`）下的 `phprt.toml` 不记录产品、版本或组件选择；`[catalog]` 只放交互
开关：

```toml
[catalog]
ask_before_online_update = true   # false = 不问、不取，直接用本地
default_answer = "y"              # 仅交互式生效；提示里按它显示“回车默认 y/n”
```

| 方式 | 行为 |
| --- | --- |
| 默认 / `ask_before_online_update = true` | 询问一次；回车按 `default_answer` |
| `ask_before_online_update = false` | 不问、不取，直接用本地（开发测试常用） |
| `--refresh` | 跳过询问，直接取；失败按错误处理 |
| `--no-refresh` | 跳过询问，不取 |
| `--offline` | 不联网，用本地 |
| `--lock` | 跳过交互；按 state 记录的版本解析，缺版本就报错 |

- 命令行显式参数优先于配置：`ask_before_online_update = false` 加 `--refresh` 仍然取。
- `--refresh` 是显式请求；即使这次不会构建（例如未安装的 `add`），也取一次。
- `--offline` 以前只约束下载；阶段 1 起同时禁止取 catalog。
- 提示里的默认值按 `default_answer` 显示；示例写的是 `y`，配置成 `n` 时不能还打印
  「回车默认 y」。
- `--refresh` 与 `--offline` / `--lock` / `--no-refresh` 同时出现时报错。
- 标准输入不是终端（CI、管道）时按 `n` 处理，并打印「非交互环境，跳过获取，使用本地」；
  `default_answer` 不生效。`--refresh` 可以显式强制取。
- 配置值非法（不是 true/false，`default_answer` 不是 y/n）直接报错，不忽略。
- 交互式 EOF 当 `n`，避免 CI 意外联网。

发布地址由发行包在编译时内置，可用 `PHPRT_CATALOG_URL` 覆盖（镜像、内网、测试）：

```bash
PHPRT_CATALOG_URL=https://catalog.example.com/phprt cargo build --release
```

源码构建默认没有内置地址：地址为空时跳过在线检查并打印一行，不影响安装；`--refresh`
遇到地址为空直接报错。

#### 5.0.6 失败、退出码和 sha256

- 交互式 `y` 取数失败：失败的组件保留本地数据，其余组件照常更新，安装继续；
  整批都没取到时打印本地数据时间。
- `--refresh` 失败：直接报错，不用旧数据，交给调用方重试。
- 单个组件失败：保留该组件上一次的数据，其余组件照常更新。
- 交互式取数失败不改变安装的退出码；`--refresh` 失败按错误退出。
- 分片里的补丁缺 `sha256`：该组件本次不更新，保留本地数据并报告 `✗`，不挑一个更旧的
  补丁顶上；提示等待维护者修复。
- 下载源码时按发布方给的 `sha256` 校验；用户不计算、不回填。
- 用户命令没有 `--fill-sha256`，也不会隐式触发维护者的回填。

### 5.1 维护者

```bash
phprt catalog update [组件...] [--fill-sha256] [--dry-run]
phprt catalog publish --out dist/catalog
```

- `update`：查上游、只升已有线、sha256 下载后计算、写前校验、写前备份。语义见
  [CATALOG-UPDATE.md](CATALOG-UPDATE.md)。
- `publish`：把 `catalog.toml` 拆成组件分片，校验每条补丁都有 sha256，写到
  `<out>/latest/`。不访问上游，纯数据变换，可重复执行。

### 5.2 没有发布地址时

源码构建默认没有内置 catalog 地址，也没有配置 `PHPRT_CATALOG_URL` 时，在线检查会跳过并
打印一行。发行包可以在编译时设置 `PHPRT_CATALOG_URL` 把地址内置进去；运行时同名环境
变量优先。此时用户拿新数据的方式仍是更新 recipes 目录（`git pull`，或安装新发行的版本包），
然后再安装或升级：

```bash
phprt install php@8.5     # 首次安装
phprt update php@8.5      # 已有安装，升到新补丁
```

`install` 和 `update` 都只跟随当前安装闭包，catalog 里多出来的 php、swoole 条目不会让
它们多编译、多下载任何东西。**用户不需要为了「只用 nginx」去裁剪 catalog。**

用户侧不需要、也不会运行 `catalog update`，更不需要填 sha256；这两件事只在维护者流程里。

**维护者**：

```bash
phprt catalog update --dry-run                 # 先看计划，不下载、不写文件
phprt catalog update php openssl zlib          # 分批跑，失败面小，diff 好 review
phprt catalog update --fill-sha256 xdebug      # 只补缺失的哈希
git diff recipes/catalog.toml                  # 只 review 数据改动
```

一次全量跑失败时，按报告里的组件名重跑点名更新即可；已经写进去的补丁不会重复写。

**发布**：

```bash
phprt catalog update --fill-sha256
phprt catalog publish --out dist/catalog
# 把 dist/catalog/latest/ 上传到静态主机
```

放进定时流水线后，产物是新的 `latest/components/*.toml` 和 `latest/stamp`；用户下次
`install` / `update` 回答 `y` 就能拿到。

### 5.3 按产品裁剪

维护者用 `plan` 的 JSON 取闭包里的依赖名，再点名更新。bundled 组件不需要 catalog 条目：

```bash
phprt plan nginx@1.29 --json \
  | jq -r '.order[] | select(.kind == "dep") | .name' \
  | sort -u
# 把结果和 nginx 本身一起传给 catalog update
phprt catalog update nginx openssl pcre2
```

用户侧不需要这一步：交互检查按闭包自动只取用到的组件分片。

## 6. 解析与优先级

### 6.1 用哪份数据

| 场景 | 用的数据 | 补丁 |
| --- | --- | --- |
| `install` / `update` / 已安装产品的 `add` / 重编 `remove` 且 `y` | 基线 + 更新后的本地分片 | 该线最大补丁 |
| 同上且 `n` | 基线 + 当前本地分片 | 该线最大补丁 |
| `add`（未安装）/ 不用重编的 `remove` | 不改数据，只改方案 | 不解析新补丁 |
| `--lock` | 基线 + 本地分片，按 state 记录的版本 | state 记录的版本 |
| `--offline` | 基线 + 当前本地分片 | 该线最大补丁 |
| `ask_before_online_update = false` / `--no-refresh` | 基线 + 当前本地分片 | 该线最大补丁 |

`--lock` 不询问、不联网；state 里的版本在合并后的 catalog 里找不到时报错，不偷偷换最新。
`state` 只记录实际装过的 `line` / `version`，不复制 `url` / `sha256`（见 [STATE.md](STATE.md)）。

### 6.2 数据日期

本地 `stamp` 记录最近一次真正写入新数据的时间。整批都没取到时打印这个时间，让人能判断
这次是不是没拿到最新数据；部分组件失败时只说明那些行继续用本地版本，不拿新 `stamp`
冒充它们的数据时间。没有本地分片时使用随包基线，不打印日期。

`stamp` 只保留最近一次，不留历史。阶段 1 能回答「装了哪个补丁」，不能回答「当时用的是
哪批数据」。需要精确复现时靠阶段 2 的快照 id，见
[CATALOG-SNAPSHOT.md](CATALOG-SNAPSHOT.md)。

## 7. 完整性与信任（阶段 1）

| 保护 | 谁做 | 防住什么 |
| --- | --- | --- |
| 补丁 `sha256` | 维护者 `catalog update` 下载后计算，`publish` 校验齐全 | 下载到的源码和发布数据不一致 |
| HTTPS | 发布主机 | 传输途中被替换 |
| 本地合并校验 | 客户端 | 同一版本出现两个不同的非空 `sha256` |

阶段 1 没有签名：发布主机被控制时，攻击者可以给整套分片换一份自洽的数据。这和今天的
代码仓库被控制是同一级别的信任，不夸大。要防住主机被控，需要阶段 2 的签名，见
[CATALOG-SNAPSHOT.md](CATALOG-SNAPSHOT.md)。

**签名也不证明上游可信。** 它只证明「这份数据是 phprt 维护者发布的」；上游被控时，
签名照样覆盖恶意 tarball 的哈希。上游自带的校验和可以做交叉核对，放在发布流程里。

## 8. 迁移路径

### 阶段 0：只改用法和文档（现在）

- 维护者和用户的路径分开：维护者跑 `catalog update`，用户 `install` / `update`。
- 用户拿新数据靠更新 recipes 目录或发行包。
- 不改代码、不改文件格式。

### 阶段 1：发布分片 + 用户侧检查

- `catalog publish` 拆分组件分片，校验 sha256 齐全；
- 本地 catalog 目录、基线与分片合并；
- `install` / `update` / `add` / `remove` 按 5.0 询问，只取闭包分片；
- `phprt.toml` 加 `ask_before_online_update` / `default_answer`；
- `--refresh` / `--no-refresh` 按 5.0.5；`--offline` 扩展到整个命令；
- 维护者 `catalog update` 不变。

### 阶段 2：快照、manifest、签名

见 [CATALOG-SNAPSHOT.md](CATALOG-SNAPSHOT.md)。用户侧的提示、配置、并发和显示不变，
只换取数后端和本地布局。

## 9. 取舍与风险

| 取舍 | 代价 | 缓解 |
| --- | --- | --- |
| 用户只读发布数据 | 必须先发布，最新补丁受发布频率限制 | CI 定时 `update` + `publish`；失败时明确显示数据时间 |
| 每个组件一个分片 | 发布目录文件变多 | 每个文件很小；客户端只取闭包 |
| 单文件继续做源 | 发布前仍是一个文件 | `publish` 纯变换，可重复执行 |
| 默认询问 | 每次构建多一步 | `phprt.toml` 关闭；`--no-refresh` / `--offline` 跳过 |
| `add` 已安装时也要询问 | 多一次交互 | 只有会立即编译时才问；未安装不问 |
| 阶段 1 无签名 | 发布主机被控可换数据 | HTTPS + 发布主机权限收敛；阶段 2 加签名 |

主要风险不是技术，而是**把两种角色又混回去**：例如让 `install` 跑维护者命令、写仓库、
算哈希，或让用户直接运行 `catalog update`。出现这些迹象时，回到第 3 节的原则检查。

## 10. 验收场景

阶段 1：

1. **首次安装**：`install php@8.5` 先列闭包并询问；回车后只取这些组件的分片，更新本地
   catalog，重新算方案，再下载源码、构建；不运行 `catalog update`，不计算哈希。
2. **不取**：输入 `n`、`--no-refresh`、`--offline` 或配置
   `ask_before_online_update = false` 时不联网，直接用本地。
3. **已安装无变化**：本地也没有更新时，再跑 `install php@8.5` 不询问；按重复安装提示
   处理，升级走 `update`。
4. **update**：列出已装版本和本地版本，`↑` / `=` 正确；`y` 后重新取分片并重算方案。
5. **add**：已安装时先询问再编译；未安装时只记方案，不询问、不下载。
6. **remove**：不用重编时不询问；需要重编时先确认，再问补丁，默认 `n`。
7. **lock**：`--lock` 跳过交互；不联网；state 版本缺失时报错。
8. **refresh 失败**：交互式 `y` 失败回退本地并打印数据时间，安装继续；`--refresh` 有
   组件失败直接报错。
9. **并发**：6 个假组件、每次获取 1 秒，总耗时约 3 秒（同主机 2 个），不是 6 秒。
10. **显示**：终端先列「等待」，再「获取中」，最后逐个 `✓/✗`；非终端逐行输出。
11. **单组件失败**：失败组件保留上一次数据，其余更新；安装不中断。
12. **sha256**：获取阶段不下载源码；下载时按分片哈希校验；缺哈希时该组件不更新、
    保留本地数据。
13. **只用 nginx**：只请求 nginx、openssl、pcre2 的分片，网络日志里没有 php、swoole。
14. **合并**：随包基线比本地分片新时不降级；本地分片新增的补丁参与解析；同一版本哈希
    冲突时报错。
15. **publish**：每个组件一个文件、全部线齐全、全部补丁有 sha256；分片段重复执行输出
    一致，`latest/stamp` 记录发布时间；缺哈希时失败且不写文件。
